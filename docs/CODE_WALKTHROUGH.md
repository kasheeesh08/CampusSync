# CampusSync: code walkthrough (for the demo)

## 1. Open the project
Android Studio → **Open** → `<repo>\app` (the Flutter project; the parent folder also holds docs, tools and Firebase config). If Android Studio asks for the Flutter SDK, point it to `<flutter-sdk>`. Run configurations: `lib/main.dart` (student app) and `lib/main_admin.dart` (admin dashboard, run on Chrome).

## 2. Entry points
- **`lib/main.dart`**: `main()` calls `bootstrap(adminApp: false)` (`lib/app/bootstrap.dart`), wraps the resulting `AppState` in a `ChangeNotifierProvider`, and builds `CampusSyncApp`. `_Root` picks the screen from `AppState.stage`: loading, welcome, register, verify email, pending approval, or the 5-tab `HomeShell` (Campus, Timetable, Rooms, Updates, Me).
- **`bootstrap()`** decides the backend:
  - No `CAMPUSSYNC_BACKEND` (or `=demo`) → **demo mode**: `DemoRepository` over the bundled JSON from `loadBundledSeed()` (`lib/data/seed_loader.dart`). The release APK runs in this mode.
  - `--dart-define=CAMPUSSYNC_BACKEND=emulator` → `FirestoreRepository` against the **local Firebase emulators** (test environment, labelled in the UI).
  - `--dart-define=CAMPUSSYNC_BACKEND=live` → `FirestoreRepository` against the **real (live) Firebase project** (options generated by FlutterFire in `lib/firebase_options_live.dart`). Live is never selected implicitly. The selection logic is `FirebaseConfig` in `lib/firebase_options.dart`.
- **`lib/main_admin.dart`**: the same bootstrap with `adminApp: true`. It shows `AdminGate` → `AdminShell` (`lib/ui/admin/`). Run with `flutter run -d chrome -t lib/main_admin.dart`.

## 4. How a timetable is loaded and shown
1. Source PDFs were transcribed by `tools/build_seed.py` into `app/assets/seed/timetables.json` (versions with entries, effective dates, provenance).
2. `AppState.refresh()` calls `repo.fetch()` and gets a `CampusData` snapshot. Students only receive **published** versions.
3. The `AppState.schedule` getter builds a `ScheduleService` (`domain/schedule.dart`). `dayView()` takes the student's group, filters by lab batch, swaps in chosen open electives, and fills gaps as "no class listed". Breaks and library periods are free periods.
4. `TimetableScreen` (`ui/timetable/timetable_screen.dart`) renders the day and week views from those slots.

## 5. How room status is decided
`AvailabilityEngine.check(roomId, date, start, end)` in `domain/availability.dart`:
1. For every **active** group it picks `effectiveVersion()`, the highest published version covering the date.
2. It collects that day's non-cancelled entries in the room and tests overlap.
3. The result is **occupied** if any entry overlaps. **Free (verified)** applies only if the admin declared coverage complete *and* every group is published. Otherwise the room is **"No class listed · unverified"**. Inactive or non-schedulable rooms are unavailable.

The Rooms tab (`ExplorerScreen`) and the Academic Block interior (`BuildingInteriorScreen`) both draw `FloorPlanView` and `RoomDetailsSheet` from `ui/rooms/floor_plan.dart`, so they always agree. Timetable data never claims a room is physically empty.

## 6. How focus sessions work and persist
- `FocusSession` (`domain/focus.dart`) stores `startedAt`, `pausedTotal` and `pausedAt`. Remaining time is computed against the clock (`remainingAt(now)`), not counted down in memory. `settle(now)` marks a session completed at its exact due time, even if the app was closed.
- `AppState.startFocus` / `pauseFocus` / `resumeFocus` / `endFocus` save through `FocusRepository`. The only implementation, `LocalFocusRepository` (`data/focus_repository.dart`), uses device SharedPreferences and is labelled "Saved on this device only".
- `settleFocus()` runs at start-up, every second on the focus screens, and when the app returns to the foreground (`HomeShell.didChangeAppLifecycleState`).
- A running session adds a completion reminder to `planReminders()`. Pausing removes it and resuming reschedules it (`AppState.rescheduleReminders`).
- UI: `LibraryStudyScreen` (`ui/world/library_study.dart`). The desk layout there is illustrative.

## 7. Admin dashboard
Same code base, entry point `lib/main_admin.dart`. Sections live in `ui/admin/`: timetables (CSV/JSON upload → preview → validate → draft → publish → rollback), groups, rooms and floor mapping, announcements, exams and calendar, students, administrators, audit log, settings. Writes go through `FirestoreRepository`, which writes an audit record in the same batch. Permissions are enforced by `firebase/firestore.rules`.

## 9. What is live versus demo/local
| Feature | Status |
|---|---|
| Timetables, rooms, exams, calendar in the APK | Bundled demo data from the official documents (no server) |
| Sign-in, registration, approval, admin publishing, security rules | Implemented and verified against the **local Firebase emulator**; no real project configured |
| Focus sessions, character outfit colour, reminder preferences | Device-local only |
| Local reminders | Scheduling verified on the emulator; focus-completion delivery not yet observed |
| Push notifications (FCM), multiplayer, server-synced sessions | Not implemented |
